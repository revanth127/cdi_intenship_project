# Order-to-Audit System Backend

Backend for a food manufacturer "Order-to-Audit" system (salesmen order placement, admin GST invoicing, production supervisor BOM-based run logging, and accountant reports).

## Tech Stack

- **Framework**: FastAPI (Python 3.12)
- **Database**: PostgreSQL 16
- **ORM**: SQLAlchemy 2.x (Typed, `Mapped[]` style with declarative constraint naming)
- **Migrations**: Alembic
- **Validation & Settings**: Pydantic v2 & `pydantic-settings`
- **Authentication**: JWT (OAuth2 Password Bearer flow with `exp`, `sub`, and `role` claims)
- **Authorization**: Granular Role-Based Access Control (RBAC)
- **Audit Logging**: JSONB audit trail (`audit_logs`) capturing before/after state
- **Monetary Storage**: Strict integer paise arithmetic (`utils/money.py` using `Decimal` & `ROUND_HALF_UP`)

## JWT Authentication Flow & Architecture

1. **Login Request**:
   * Client sends credentials (`username` = email, `password` = plain text password) to `POST /api/v1/auth/login` formatted as `application/x-www-form-urlencoded` (`OAuth2PasswordRequestForm`).
   * This allows Swagger UI's **Authorize** modal to work out of the box.
2. **Credential Verification**:
   * Server looks up user by email, verifies bcrypt password hash using constant-time verification.
   * If user is inactive or credentials mismatch, returns a generic `401 Unauthorized` without revealing whether the email or password was wrong.
3. **Token Issuance**:
   * Server signs a JWT using HMAC-SHA256 (`HS256`) and the server `SECRET_KEY`.
   * Claims include:
     * `sub`: User ID (`string`)
     * `role`: User Role (`ADMIN`, `SALESMAN`, etc.)
     * `type`: Token type (`access` or `refresh`)
     * `iat`: Issue timestamp (UTC)
     * `exp`: Expiration timestamp (UTC)
4. **Request Authorization**:
   * For protected endpoints, client sends header: `Authorization: Bearer <access_token>`.
   * `get_current_user` dependency decodes the token, validates signature and expiration, verifies `type == "access"`, and verifies user is active in DB.
5. **Role Guard**:
   * `require_roles(*roles)` inspects the loaded user's role. If not in the allowed list, rejects request with `403 Forbidden`.
6. **Refresh Token Tradeoff**:
   * *Tradeoff*: Stateless JWT refresh tokens allow clients to renew access tokens without storing sessions on the server. However, immediate server-side revocation (forced logout) is impossible without maintaining a token revocation blacklist in Redis or PostgreSQL. For high-security banking, a server-stored refresh token table with rotation is preferred; for microservice performance, stateless tokens minimize database latency.

                                                     |

                          |                                                     |
                     [Shortage > 0]                                      [All In Stock]
                          |                                                     |
                  ROLLBACK & RETURN                                             v
              HTTP 409 Conflict Shortages               2. Lock Item Rows (SELECT ... FOR UPDATE)
                                                                                |
                                                                                v
                       +--------------------------------------------------------------------------------+
                       |                       POST IMMUTABLE STOCK MOVEMENTS                           |
                       +--------------------------------------------------------------------------------+
                       |                                                                                |
                       |  A. PRODUCTION_ISSUE (Raw Materials & Packaging)                               |
                       |     - Item: Flour (-40,000 g)       @ WAC 4.312500 paise/g -> -172,500 paise   |

### 2. Interview-Ready Explanation: BOM Consumption & Variance Computation

#### Question: How does your system compute BOM consumption, finished goods valuation, and variance alerts?

> **Response**:
>
> 1. **BOM Scaling & Integer Base Units**:
>    A finished goods recipe (`BOM`) defines standard requirements for a baseline output (e.g. 1 standard batch = 200 packets of Murukku 200 g requiring 40,000 g flour, 10,000 ml oil, 1,200 g spice mix, 200 pouches, and 10 cartons). When creating a production run, the user specifies standard batches (e.g. 1.0) or target packets. The system scales each BOM line into integer base units using `ROUND_HALF_UP`:
>    $$\text{planned\_qty\_base} = \text{round}(\text{quantity\_per\_batch} \times \text{batches}, \text{ROUND\_HALF\_UP})$$
>    Floating-point numbers are strictly forbidden to eliminate binary floating-point rounding errors.
>
> 2. **Packaging Consumption Logic (Pouches vs Cartons)**:
>    - **Primary Packaging (Pouches)**: Primary packaging directly encases good output packets plus scrap. Actual consumption is:
>      $$\text{actual\_consumption} = \text{pieces used in good packets} + \text{pieces damaged}$$
>      In the benchmark, 188 good packets were produced and 6 pouches were damaged; total actual consumption is $188 + 6 = 194$ pouches.
>    - **Secondary Packaging (Cartons)**: Secondary shipper cartons are **not auto-computed**. Although 188 packets divided by 20 packets/carton mathematically rounds up to 10 cartons ($188 / 20 = 9.4 \to 10$), on the factory floor operators packed 9 cartons (with partial remaining packets). Therefore, secondary carton usage is entered manually by the production operator as actual.
>
> 3. **Mathematical Variance Computation & Tolerance Flagging**:
>    - **Line Variance Percentage**:
>      $$\text{variance\_pct} = \left(\frac{\text{actual\_qty} - \text{planned\_qty}}{\text{planned\_qty}}\right) \times 100$$
>    - **Yield Variance Percentage**:
>      $$\text{yield\_variance\_pct} = \left(\frac{\text{actual\_good\_packets} - \text{expected\_output\_packets}}{\text{expected\_output\_packets}}\right) \times 100$$
>    - **Strict Tolerance Flagging**:
>      A line or yield is flagged if and only if:
>      $$\text{abs}(\text{variance\_pct}) > \text{effective\_tolerance}$$
>      The rule is **strictly greater-than (`>`)**, not greater-than-or-equal (`>=`).
>      - Oil: Planned 10,000 ml, Actual 10,500 ml $\implies +5.00\%$. Since $5.00\% > 3.00\%$, **Flagged**.
>      - Yield: Expected 200 pkts, Actual 188 pkts $\implies -6.00\%$. Since $|-6.00\%| = 6.00\% > 3.00\%$, **Flagged**.
>      - Cartons: Planned 10, Actual 9 $\implies \frac{9 - 10}{10} \times 100 = -10.00\%$. Since $|-10.00\%| = 10.00\% > 3.00\%$, **Flagged** (this correctly alerts management that packaging consumption significantly deviated from the baseline standard).
>      - Pouches: Planned 200, Actual 194 $\implies \frac{194 - 200}{200} \times 100 = -3.00\%$. Since $|-3.00\%| = 3.00\%$, and $3.00\% > 3.00\%$ is **False**, pouches are **not flagged** (respecting the strict borderline tolerance rule).
>
> 4. **Finished Goods Valuation (Absorption of Material Costs)**:
>    During posting, materials are issued at the prevailing Moving Weighted Average Cost at that exact moment. The finished product cost absorbed into finished inventory is strictly:
>    $$\text{Unit FG Cost (paise)} = \frac{\sum \text{Value of All Consumed Materials (paise)}}{\text{Actual Good Packets Produced}}$$
>    For Murukku 200 g: $\frac{405,500 \text{ paise}}{188 \text{ packets}} = 2156.914894 \text{ paise/packet}$ (Rs 21.57). This ensures total inventory valuation is preserved with zero monetary drift.
